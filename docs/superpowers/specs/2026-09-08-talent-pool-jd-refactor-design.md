# 人才库与 JD 管理重构设计

**状态：** 已定稿，待用户复核  
**日期：** 2026-09-08  
**范围：** 桌面端人才库、简历解析、候选人检索与匹配、JD 管理、候选人硬删除、学校映射、存量数据回填

## 1. 背景与目标

本次重构解决人才库信息密度低、检索语义不清、方向功能冗余、JD 要求不直观，以及候选人删除后流程历史无法独立保留等问题。

目标如下：

1. 收窄左侧导航栏，并统一为“深色导航 + 浅色内容”的现代 SaaS 视觉风格。
2. 候选人列表使用固定高度单行展示，不再展示工作经历和项目经历明细。
3. 列表字段可配置、可编辑，并支持候选人物理删除。
4. 搜索和匹配支持关键词、向量、混合三种模式。
5. 姓名、公司、职位、学校、城市等字段筛选必须在对应解析字段中命中，不允许语义推测。
6. 使用结构化教育经历和学校映射支持 985、211、双一流、普本、大专及海外 QS 2026 检索。
7. 为候选人和 JD 生成可编辑的 AI 画像。
8. 删除简历和 JD 侧的方向功能，但保留组织架构中语义不同的部门业务方向字段。
9. 删除候选人时保留流程、轮次和事件，并以候选人快照继续展示历史。
10. 为存量数据提供可暂停、可重试的画像补齐、学校映射和索引重建任务。

## 2. 设计原则

- 采用兼容迁移式重构，不进行全量数据库推倒重建。
- 精确筛选与搜索模式相互独立：筛选决定“是否合格”，搜索模式决定“如何召回和排序”。
- 解析证据不足时返回空值，不编造年龄、城市、学校等级或 QS 排名。
- 人工修改优先于自动解析；重新解析和后台回填不得覆盖人工修改。
- 关键词索引与向量索引使用不同文本，避免字段边界和语义召回互相污染。
- 硬删除的数据库变更先提交，物理文件清理通过幂等任务完成，避免数据库回滚后文件已经丢失。
- 新旧 `parsed_data` 在迁移期保持可读，前端只消费新的稳定接口字段。

## 3. 已确认的产品决策

### 3.1 搜索模式

搜索保留三种模式：

- `keyword`：仅关键词召回。
- `vector`：仅向量召回。
- `hybrid`：关键词与向量并行召回后融合。

首次使用默认 `hybrid`，之后按用户维度在本地保存上次选择。人才库搜索、JD 正向匹配和候选人反向匹配都显式传递当前模式，后端不依赖隐含状态。

### 3.2 手机号匹配

手机号在去除空格、连字符和国家码 `+86` 后执行整号匹配。手机号不进入全文索引或向量文本，也不支持手机号语义或子串召回。

### 3.3 候选人删除

候选人执行物理删除。若存在流程记录，先保存候选人快照，再解除流程与候选人的外键关联；流程、面试轮次、事件和备注继续保留。

### 3.4 存量数据

新导入数据实时生成画像并建立新版索引。存量候选人和 JD 通过可暂停、可重试、可观测进度的后台任务逐步补齐，不在数据库升级时同步调用 LLM。

## 4. 范围与非目标

### 4.1 本次范围

- `desktop/src/App.tsx`、`desktop/src/api/client.ts` 及相关样式和组件。
- 简历/JD 结构化解析、归一化、编辑与索引同步。
- 候选人搜索、JD 正向匹配、候选人反向匹配。
- 学校参考数据模型、国内名单种子和 QS 2026 导入能力。
- 候选人物理删除及流程快照。
- 简历/JD 方向功能完整移除。
- 数据库迁移、索引版本升级、存量回填和相关测试。

### 4.2 非目标

- 不删除组织架构 `Department.business_direction` 字段。
- 不在没有可靠数据源时自动猜测海外学校 QS 排名。
- 不把工作职责和项目详情从简历存储中删除；它们仅退出列表展示和新版检索文本。
- 不在本次引入通用学校管理后台；先提供查询、导入和映射状态能力。
- 不重写整套桌面应用，也不顺带重构无关模块。

## 5. 候选人领域模型

### 5.1 结构化教育经历

现有单一 `school`、`highest_degree` 和 `graduation_year` 无法表达“北京大学硕士、清华大学本科”。在 `ParsedResume` 和 `NormalizedResume` 中新增 `educations`：

```python
class ParsedEducation(BaseModel):
    school: str | None = None
    degree: str | None = None
    major: str | None = None
    graduation_year: int | None = None
    country_region: str | None = None
    school_tags: list[str] = Field(default_factory=list)
    qs_year: int | None = None
    qs_rank: int | None = None
```

迁移期继续输出以下兼容字段，但它们由 `educations` 派生，不再作为唯一事实来源：

- `school`：最高学历对应学校；无法判断时取第一条有效教育经历。
- `highest_degree`：所有教育经历中的最高学历。
- `graduation_year`：本科毕业年份；无本科时取最高学历毕业年份。
- `school_level`：最高学校标签的兼容展示值。
- `qs_rank`：有效 QS 排名中的最优名次。

### 5.2 工作经历

扩展工作经历，以可靠确定最近公司、职位和城市：

```python
class ParsedExperience(BaseModel):
    company: str | None = None
    title: str | None = None
    start_date: str | None = None
    end_date: str | None = None
    location: str | None = None
    summary: str | None = ""
    industry: str | None = None
```

`current_company` 和 `current_title` 由最近一段有效经历派生。优先按结束时间排序；“至今”高于具体结束时间；日期缺失时保留解析顺序，并记录低置信度来源。

### 5.3 年龄

年龄派生优先级：

1. 简历明确年龄，使用该年龄。
2. 有出生年份，使用 `当前年份 - 出生年份`。
3. 有本科毕业年份，使用 `22 + 当前年份 - 本科毕业年份`。
4. 均无证据时置空。

结果为整数，并保存 `age_source = explicit | birth_year | bachelor_graduation | manual | unknown`。计算结果必须经过合理区间校验；异常值置空并写入解析诊断。

年龄推算必须直接查找 `educations` 中的本科记录，不得把兼容字段 `graduation_year` 中可能存在的硕士或博士毕业年份用于年龄计算。

仓库现有 `_compute_age` 已采用正确的本科毕业推算思路，本次应保留逻辑、扩充教育经历来源并补充回归测试。

### 5.4 所在城市

城市派生优先级：

1. 简历明确的现居城市。
2. 最近一段工作经历中的地点。
3. 已知公司地址映射中的城市。
4. 无可靠证据时置空。

保存 `location_source = resume | recent_experience | company_mapping | manual | unknown`。公司注册地、总部所在地和实际工作地不一定相同，因此公司地址推断结果必须标记来源，且不得在多个城市中随意选择。

### 5.5 工作年限

底层继续保留原始精度，列表和接口展示使用四舍五入后的整数。人工编辑值保存在 `manual_overrides`，重新解析不得覆盖。

### 5.6 AI 候选人画像

新增 `ai_profile_summary: str | None`。画像只能基于结构化简历证据生成，建议覆盖：

- 教育背景；
- 核心工作年限；
- 最近公司和职位；
- 主要技能及行业经验；
- 可从履历证据支持的优势和适合岗位。

新简历优先在现有 LLM 结构化解析请求中同时返回画像，避免每份简历增加一次模型调用。画像生成失败不得阻断简历入库，应置空并写入 `extraction_diagnostics`。

当姓名、教育、年限、城市、公司、职位或技能发生人工修改时：

- 立即同步关键词索引和结构化过滤字段；
- 将自动生成画像标记为“可能已过期”；
- 提供“重新生成画像”操作；
- 若画像本身经过人工编辑，不自动覆盖。

画像元数据保存 `ai_profile_source`、`ai_profile_input_hash` 和 `ai_profile_stale`，用于区分自动生成、人工编辑、输入是否变化及是否需要重新生成。

## 6. 字段行为矩阵

| 字段 | 列表展示 | 可编辑 | 关键词文本 | 向量文本 | 字段筛选 |
| --- | --- | --- | --- | --- | --- |
| 姓名 | 是 | 是 | 是 | 是 | 字段内关键词 |
| 手机号 | 是 | 是 | 否 | 否 | 规范化整号匹配 |
| 教育经历 | 是 | 是 | 是 | 是 | 学校别名/学历/标签/QS |
| 年龄 | 是 | 是 | 可读文本 | 是 | 数值范围 |
| 所在城市 | 是 | 是 | 是 | 是 | 字段内关键词 |
| 工作年限 | 是 | 是 | 可读文本 | 是 | 数值范围 |
| 公司 | 最近一段 | 最近一段 | 全部经历 | 最近一段 | 全部公司字段内关键词 |
| 职位 | 最近一段 | 最近一段 | 全部经历 | 最近一段 | 全部职位字段内关键词 |
| 技能 | 否 | 详情中维护 | 是 | 是 | 包含/排除关键词 |
| AI 画像 | 是 | 是 | 是 | 主体内容 | 否 |
| 工作职责正文 | 否 | 详情中维护 | 否 | 否 | 否 |

“列表不展示”不等于“删除数据”。工作与项目明细继续保存在简历版本中，用于详情、审计和以后重新解析。

## 7. 学校映射

### 7.1 数据模型

新增学校参考表，建议字段：

```text
canonical_name       学校标准名
normalized_name      用于查找的归一化名称
aliases              别名列表
country_region       国家或地区
institution_type     本科院校、大专、海外院校等
tags                 985、211、双一流、普本、大专、海外
qs_year              排名年份
qs_rank_start        排名或区间起点
qs_rank_end          排名或区间终点
rank_display         原始展示文本，例如 1201-1400
source               builtin 或 imported
updated_at           更新时间
```

985、211、双一流是重叠属性，必须使用标签集合，不能使用互斥的单一 `level` 字段。

### 7.2 名称归一化

学校名称查找至少执行：

- Unicode NFKC 归一化；
- 去除多余空格和常见标点；
- 英文名称大小写不敏感；
- 标准名和别名同时匹配；
- 对未识别学校返回“待映射”，不自动归类为普本。

### 7.3 数据来源

- 内置国内 985、211、双一流名单。
- 普本和大专按明确的院校类型数据映射，未知学校不自动降级。
- 海外 QS 2026 通过 JSON/CSV 导入；导入时校验年份、标准名、别名、排名及排名区间。
- 保存排名年份和来源，为以后并存 QS 2027 等版本留出空间。

### 7.4 接口

建议提供：

- `GET /api/schools`：分页查询学校及映射状态。
- `POST /api/schools/import`：导入并校验 JSON/CSV 数据。
- `POST /api/schools/resolve`：预览名称解析结果，不写入候选人。
- `GET /api/schools/import-template`：下载固定字段模板。

## 8. 搜索架构

### 8.1 索引记录

新版索引为每个候选人当前简历版本保存一条主记录：

```text
candidate_id
revision_id
keyword_text
vector_text
vector
name_terms
school_terms
company_terms
title_terms
location_terms
skills
age
total_years
highest_degree
school_tags
qs_rank
candidate_status
```

关键词文本与向量文本不得继续复用当前单一 `content`。

### 8.2 关键词文本

`keyword_text` 包含：

- 姓名；
- 全部教育经历的学校、别名、学历；
- 城市；
- 全部工作经历的公司和职位；
- 技能；
- AI 画像；
- 年龄、年限、QS 等可读文本。

不包含手机号、工作职责正文和项目正文。

### 8.3 向量文本

`vector_text` 包含：

- AI 候选人画像；
- 教育背景；
- 城市和工作年限；
- 最近公司和职位；
- 主要技能。

向量不包含手机号、方向字段以及逐段工作或项目正文。该文本兼顾画像语义和稳定结构化证据，比仅使用 AI 画像更抗总结遗漏，也比现有全量经历分块更少噪声。

### 8.4 三种模式

- `keyword`：只调用 `search_fts`，不调用 embedding；不使用语义重排改变纯关键词排序。
- `vector`：生成查询向量，只调用 `search_vector`；允许使用配置好的语义重排。
- `hybrid`：并行执行 FTS 和向量召回，融合、按候选人去重后重排。

空查询且存在筛选条件时执行纯过滤搜索，不调用 embedding。

### 8.5 精确筛选

字段筛选先于最终排序执行，并且在三种模式下语义一致：

- 姓名只检查 `name_terms`。
- 公司检查全部 `company_terms`。
- 职位检查全部 `title_terms`。
- 学校检查标准名及别名形成的 `school_terms`。
- 城市只检查 `location_terms`。
- 学历、学校标签、年龄、年限、QS 使用结构化比较。
- 排除技能在完整技能字段上执行硬排除。

字段关键词使用归一化后的包含匹配或分词命中。某字段的关键词出现在 AI 画像或其他字段中，不得使该字段筛选通过。

### 8.6 API 合同

候选人搜索请求新增：

```json
{
  "query": "高级产品经理",
  "mode": "hybrid",
  "filters": {
    "name": "张",
    "company": "腾讯",
    "title": "产品经理",
    "school": "北京大学",
    "locations": ["上海"],
    "min_age": 28,
    "max_age": 35
  }
}
```

`mode` 必须为 `keyword | vector | hybrid`。非法值返回 422。后端应继续返回现有的成功、降级、索引未就绪和服务错误状态；向量服务故障时，`vector` 模式不得静默变成关键词模式，`hybrid` 模式可以返回带降级原因的关键词结果。

### 8.7 索引版本

由于物理字段、分块方式和向量文本均改变，必须提升 `schema_version` 和 `chunk_version`。旧索引不兼容时显示“需要重建”，不得在旧表中混写新旧记录。

## 9. 候选人物理删除与流程快照

### 9.1 数据库变更

将 `CandidateJobCase.candidate_id` 改为可空，并把外键删除行为从 `CASCADE` 改为 `SET NULL`。为流程新增候选人快照，至少包括：

```text
candidate_name_snapshot
candidate_phone_snapshot_encrypted
candidate_email_snapshot_encrypted
candidate_profile_snapshot
candidate_deleted_at
```

手机号和邮箱快照继续使用现有加密服务，不以明文写入 JSON。

### 9.2 删除事务

`DELETE /api/resumes/candidate/{candidate_id}` 执行：

1. 锁定候选人及其关联流程，避免删除过程中新增流程。
2. 为每条流程补齐候选人快照，并将 `candidate_id` 置空。
3. 保留 `CandidateJobCase`、`CaseRound`、`CaseEvent`、历史阶段和备注。
4. 解除组织员工与候选人的绑定。
5. 删除候选人联系方式、简历文档、简历版本、临时匹配结果、纠错记录和索引同步记录。
6. 释放导入幂等声明，使相同文件以后可以重新导入。
7. 记录需要删除的索引实体和无引用 Blob。
8. 提交数据库事务。
9. 幂等清理搜索索引和无引用物理文件；失败时进入可重试清理任务。

接口幂等：候选人已经删除时再次调用应返回稳定的已删除结果或 404，不得误删其他实体。

### 9.3 删除后的流程行为

- 继续显示姓名、加密联系方式解密结果及画像快照。
- 显示“候选人已删除”标识。
- 禁止查看简历、重新匹配、跳转候选人详情或创建新流程。
- 允许查看历史轮次、事件和备注。
- `candidate_id` 在流程 API 响应中改为可空，前端不得假设始终存在。

## 10. 人才库前端

### 10.1 布局与配色

- 导航展开宽度调整为 196–200px，折叠宽度约 64px。
- 使用石墨深色导航、浅灰内容背景和蓝色强调色。
- 在 `:root` 定义导航、背景、文字、边框、强调、成功、警告、错误和焦点状态变量。
- 同步修改 `.navigation` 与 `.workspace` 的宽度/边距，避免内容遮挡。
- 保留现有 class 命名，减少无关 JSX 改动。

### 10.2 候选人单行列表

默认列顺序：

1. 姓名；
2. 电话；
3. 学校学历；
4. 年龄；
5. 所在城市；
6. 工作年限；
7. 当前公司；
8. 当前职位；
9. AI 画像；
10. 操作。

列表使用固定高度单行记录并支持横向滚动。AI 画像可使用最多两行截断或单行省略，点击查看完整内容。工作和项目经历不再在列表中展开，但详情页继续保留。

操作区包含：查看详情、匹配、建流程、下载、强制 OCR、删除。删除必须二次确认，并明确说明流程历史会保留、简历文件会永久清除。

### 10.3 列设置

- “列设置”按钮位于“候选人”标题同一行右侧。
- 姓名和操作列固定不可隐藏。
- 其余业务列默认显示，可由用户勾选。
- 人才库列表和搜索结果共用配置。
- 使用带版本号的本地键保存，例如 `candidate-table-columns:v1`，字段变化后可安全迁移默认值。

### 10.4 编辑

- 姓名、电话、年龄、城市、年限、当前公司和当前职位支持单元格内编辑。
- 教育经历使用小型编辑弹窗，避免把学校和学历拼接文本直接写回一个字段。
- AI 画像使用多行编辑弹窗，并显示自动生成、人工编辑或待更新状态。
- 编辑成功后刷新当前记录并触发索引同步；失败时保留用户输入并显示明确错误。

### 10.5 前端组件边界

`desktop/src/App.tsx` 当前承担过多页面和业务状态。本次只拆分与改造直接相关的边界，避免继续把人才库逻辑写入该大文件：

- `CandidateTable.tsx`：普通与虚拟列表共享的列定义和单行渲染。
- `CandidateColumnSettings.tsx`：列选择与本地持久化。
- `SearchModeSwitch.tsx`：三种搜索模式选择。
- `CandidateEducationEditor.tsx`：多段教育经历编辑。
- `AiProfileEditor.tsx`：候选人/JD 画像查看、编辑和重新生成状态。

`App.tsx` 保留页面级状态和导航编排，API 类型继续集中于客户端合同，避免组件自行拼装请求。

### 10.6 后端服务边界

- `schools/reference.py`：学校名称归一化与映射，不直接依赖 HTTP。
- `resumes/profile.py`：候选人画像输入构建、哈希和生成策略。
- `jd/profile.py`：JD 画像输入构建、哈希和生成策略。
- `resumes/deletion.py`：候选人删除事务、流程快照和清理任务登记。
- `search/documents.py`：集中构建 `keyword_text`、`vector_text` 和字段词项。

API 层只负责请求校验、调用服务及错误映射，不承载删除、画像或索引构建细节。

## 11. JD 管理与匹配

### 11.1 JD 数据

`ParsedJd` 移除 `tech_direction` 和 `business_direction`，新增：

```python
candidate_profile: str | None = None
```

保留 `requirements` 中的 `MUST`、`PLUS`、`EXCLUDE`，用于硬条件、加分项、排除项和匹配解释。主表删除“岗位要求（技术+业务）”和“编辑方向”，改为展示可编辑的“候选人画像要求”。

### 11.2 画像生成

JD 解析时由现有 LLM 同时生成 `candidate_profile`。内容包括目标资历、经验、技能、行业背景及岗位特征，且必须来源于 JD 原文。

### 11.3 匹配

JD 正向匹配的查询文本由以下内容构成：

- `candidate_profile`；
- `required_skills`；
- `MUST` 要求。

删除方向兼容分后，匹配评分由召回相关性、必备技能覆盖、工作年限及其他现有可验证硬条件组成。具体权重应在实施阶段通过现有测试样本校准，不沿用删除方向分后的未归一化旧权重。

JD 正向匹配和候选人反向匹配都接收显式 `mode`：

- 关键词模式只使用词法字段；
- 向量模式使用候选人/JD 画像向量；
- 混合模式融合两路结果。

## 12. 方向功能删除边界

彻底删除简历和 JD 侧的：

- `backend/src/kerui_recruit/direction/`；
- `backend/src/kerui_recruit/api/directions.py`；
- 方向 Provider、分类器、评估服务和运行时装配；
- 搜索方向字段、方向意图加权和索引同步；
- 匹配方向兼容分、响应字段和解释；
- 简历/JD pipeline 中的方向分类与诊断；
- 前端方向类型、接口、编辑器、状态、筛选、列和抽屉；
- 方向专项测试和基准脚本；
- 存量简历/JD `parsed_data`、`review_data`、`manual_overrides` 中的方向键。

保留组织架构 `Department.business_direction`。清理时必须按模型语义和所属模块识别，不允许仅按字符串全局删除。

## 13. 存量回填与迁移

迁移分为以下阶段：

1. 数据库增加教育结构兼容能力、学校表和流程快照字段。
2. 迁移流程外键为可空并改为 `SET NULL`。
3. 清除存量简历/JD JSON 中的方向键。
4. 部署新版解析、编辑和索引构建逻辑。
5. 创建后台回填任务：学校映射、候选人画像、JD 画像、新版索引。
6. 回填完成后切换搜索读路径，并停止兼容旧索引。

后台任务要求：

- 支持暂停、继续和失败重试；
- 以候选人/JD 当前版本作为幂等键；
- 跳过已由人工填写且标记为手动字段的数据；
- 展示总数、成功数、失败数、剩余数和最近错误；
- 单条失败不阻断整个批次；
- 任务重新运行时不重复调用已成功且输入未变化的 LLM 画像生成。

## 14. 错误与降级处理

- LLM 画像失败：保留解析结果，画像为空并允许重试。
- 学校未识别：显示原始学校名和“待映射”，不猜测等级。
- 向量服务失败：`vector` 返回服务降级/失败；`hybrid` 返回关键词结果并标记降级。
- 索引未完成：搜索返回 `index_not_ready`，前端展示重建进度。
- 删除后的文件清理失败：候选人保持已删除，后台继续幂等清理并记录错误。
- 编辑导致索引同步失败：数据库修改保留，记录待同步状态并在前端提示“搜索索引待更新”。

## 15. 验收标准

### 15.1 候选人列表

- 列表和搜索结果均不展示工作经历、项目经历明细。
- 默认业务字段与操作全部处于同一候选人记录中。
- 列设置刷新应用后仍然有效。
- 所有约定字段均可编辑，人工修改在重新解析后保持。
- 年龄、工作年限均以整数展示。

### 15.2 搜索与筛选

- 三种模式都能独立调用，并在界面明确显示当前模式。
- 公司、姓名、职位、学校和城市只在对应解析字段命中时通过。
- 公司和职位筛选覆盖全部工作经历，而列表只显示最近一段。
- 手机号只有规范化整号相同时命中。
- 在向量或混合模式下，所有字段筛选仍是硬条件。
- 工作经历职责和项目正文不进入新版关键词或向量文本。

### 15.3 学校与年龄

- 可展示多段教育经历，例如“北京大学硕士、清华大学本科”。
- 985、211、双一流标签可以同时存在。
- QS 排名携带年份和数据来源，并支持区间排名。
- 无出生信息时按本科毕业年份推算年龄；无本科毕业年份时不错误使用硕士毕业年份。

### 15.4 删除与流程

- 无流程候选人可直接物理删除。
- 有流程候选人删除后，流程、轮次、事件和备注仍可查看。
- 流程显示候选人快照及“候选人已删除”。
- 删除后候选人不再出现在列表、搜索、匹配和索引中。
- 无引用简历文件最终从本地存储清除；共享 Blob 不被误删。
- 同一简历文件可以在删除后重新导入。

### 15.5 JD 与方向删除

- JD 主表展示候选人画像要求，不再展示技术/业务方向。
- JD 和候选人匹配都遵循当前搜索模式。
- 简历/JD 侧无方向接口、组件、字段、索引加权或匹配评分残留。
- 组织架构的部门业务方向保持可用。
