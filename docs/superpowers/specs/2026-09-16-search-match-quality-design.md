# 搜索与人岗匹配质量改造设计（2026-09-16）

## 目标与依据

目标是让人才库搜索、精确筛选、JD 找人和人找 JD 的结果可解释、少漏检、少误荐，并让 AI 深度复核成为前端可选步骤。本设计以 2026-09-16 的源码为准；仓库内较早的搜索、匹配和 Trae 文档只作历史背景。本文对应执行计划：`docs/superpowers/plans/2026-09-16-search-match-quality.md`。

用户已确认：数据工程按**主要职责**归类。数据平台、数据管道、服务和基础设施开发归 BACKEND；数仓分析、BI、统计分析归 DATA；以模型训练和算法研发为主要交付归 ALGORITHM。LLM Agent 的应用编排、工具调用和服务工程归 BACKEND；模型训练或算法研究归 ALGORITHM。不能仅凭职位名称判断。

## 当前代码与观察

| 问题 | 源码事实 | 可能影响 |
| --- | --- | --- |
| 向量文本混入弱语义字段 | `search/documents.py` 的候选人父向量含学校、城市、年限、近期公司和职位、全部技能；经历和项目各自生成子向量。`search/sync.py` 的 JD 索引还为每项必需技能生成短子向量。 | 会改变相似度排序并增加成本，但影响幅度必须用同一 embedding 模型、同一标注集做消融验证；不能仅凭字段长度断言。 |
| 职业方向错分及缺失 | `providers/generation_tasks.py` 在大段解析提示词里用一句枚举规则；`ParsedResume.direction` 与 `ParsedJd.direction` 为宽松字符串。`match/service.py` 对缺失方向直接排除。 | 错分会在第一轮硬筛时造成不可恢复的漏检。先前只读样本中，1111 份候选人最新版本有 248 份方向为空、82 份 OTHER、1 份非枚举值；此为当时快照，执行时重算。 |
| 搜索意图误判 | `search/query.py` 的城市子串识别会将“北京大学 后端”拆成地点“北京”和关键词“大学 后端”；`api/search.py` 忽略请求的 `limit` 并固定取 300。 | 用户未声明的硬地点条件会漏人；页数、总数和请求参数不一致。 |
| 关键词与混合检索的候选人排序 | `search/service.py` 的 smart 模式最低只要求命中 1 词；混合模式重排后固定截为 30。`search/lancedb_index.py` 按 chunk 做 RRF，然后按候选人去重。 | 多个弱命中可排在完整命中前，父子证据不能充分合并，匹配所需 50–100 候选人拿不到。 |

| 匹配硬条件与评分混合 | `match/service.py` 的 `_MIN_SCORE=0.4`，方向、年限和行业加权可使必需技能覆盖为 0 的候选人达到阈值；`and` 和“及”被 `_OR_CONNECTORS` 当作“或”。JD 查询主要取技能，职责没有被逐项检查。 | 可能误荐，并且给出的分数不代表关键职责有证据。 |

先前只读索引快照中，候选人子文档约占向量文档的 92%，JD 的单技能短子文档数量较多。这是**成本与排序风险的线索**，不是质量评测结果；活跃导入会让计数变化。

## 方案选择

1. **推荐：分层检索与实测消融。** 先修确定性错误，建立人工标注和基线；再比较简化向量文本、候选人级融合、重排及匹配规则。只有实测提升的文档变体才切换。
2. 直接删弱价值字段并重建索引：动作快，但很容易损失学校、技能或近期公司相关搜索，缺少可解释的收益证据。
3. 所有检索和匹配都交给大模型：成本、延迟和复现性不适合作为默认主链路，也无法弥补召回阶段被方向误筛掉的人。

## 搜索设计

搜索框保留关键词、向量、混合以及精确条件的能力，但默认入口给出清晰的“智能搜索”；高级模式可展开。查询先解析为可见的查询计划：关键词、同义词概念、用户**明确确认**的硬筛条件和排除条件。完整学校名、公司名以及“北京大学”等实体不再被城市子串切开。自动推断的条件以可取消的条件标签展示，只有高置信或用户明确指定的字段进入硬过滤；无法确认的词保留在检索文本中。

结构化字段的精确筛选留在数据库/索引元数据，不依赖向量相似度。姓名、手机号、学校、公司和明确字段查询优先走字段或词法通道；自然语言职责描述走混合通道。关键词 smart 模式按查询概念覆盖数、字段命中和稀有度排序，AND/OR 保持各自语义。“检索经历/项目正文”开关必须控制真实的 FTS 范围。API 返回真实 limit、游标或稳定分页、总量或准确的 `has_more`；筛选-only 查询按稳定键排序，不再无序截 300。

混合召回在**候选人级**合并父/子 chunk 的词法与向量证据：每通道先按候选人取最佳与少量补充证据，再融合，防止一个人因子 chunk 多而占满池子。重排输入由画像摘要、命中的工作/项目段和必要技能组成，不只用单个获胜 chunk。结果显示命中字段、片段与来源；阈值、权重和同义词表由标注集校准，不能凭感觉改常数。

向量文档候选方案：父向量以 AI 画像、从现有技能和项目技术栈**确定性提取**的有长度上限的技术栈概览、职业职责概述为主；不为建索引额外调用生成模型。工作/项目保留独立、长度受控的语义段；学校、城市、年限、姓名、电话号码、学历等级和原始技能枚举主要做精确元数据或词法检索。项目名称、业务场景如能解释职责，可与项目摘要合并。JD 父向量覆盖职位目标、核心职责、候选人画像及关键技术；单技能短向量默认作为消融候选项，只有证明改善召回才保留。每个变体在隔离索引运行，带 schema/chunk/文档构造版本；不可混用新旧向量。

## 职业方向设计

将方向判定做成有版本的独立规则/分类步骤，简历与 JD 共用一套分类准则、边界例子和枚举校验。模型需从主要工作交付物、职责和项目证据判断，输出 `direction`、证据位置和低/中/高置信度；无证据输出 `null`，不强猜。全栈、数据工程、Agent 工程、推荐/搜索平台、MLOps 等边界样本写入人工标注集。`ai_category` 与方向正交，不能把“AI 相关”等同算法方向。

同法审计其他由 AI 从预设值选择的字段，至少包括 JD 的 `ai_category`、`requirements.kind` 和简历的 `school_level`、`job_level`：列出允许值、现有校验、低置信/缺失处理、误选样本和下游影响。先修会触发硬筛或业务动作的字段；只用于展示的低风险字段在有标注证据后调整，不进行无范围的全量提示词重写。

匹配只把**可信且已确认**的方向作为硬过滤。方向缺失、OTHER 或低置信候选人先进入“方向待核”队列，可由用户修正或异步重判；不能被算作已通过硬筛，也不能静默消失。JD 方向未确认时暂停自动匹配并要求确认。人工修订优先于自动回填，回填按当前 revision/version 增量进行，并触发索引同步。旧简历不重新全文解析，先用已有结构化数据试分类；无足够证据的记录保留待核。

## 匹配设计

人才库和 JD 管理的“匹配”按钮统一使用一个匹配策略，不再暴露关键词/向量/混合三种技术模式。流程：

1. **资格层：** JD 状态、候选人状态、确认后的职业方向和 JD 明确标为硬条件的年限、学历、地点、排除项。必需技能需区分 AND、OR 组；只有经 JD 原文或人工确认的 MUST 才作硬条件。缺证据记为“待核”，不以综合分补偿。行业默认加分，仅明确硬要求才过滤。
2. **宽召回层：** 从 JD 挑 3–5 个区分度高的技能/职责概念做词法召回，另用完整职责与候选人画像做向量召回；两路候选人级融合。2k–5k 人规模下以 50–100 个为初始候选池参数，但由 `recall@50/100` 和延迟决定最终值。当前 33 个左右有效 JD 的反向匹配可以在硬筛后遍历合格 JD；达到规模阈值再依赖 JD 索引。
3. **确定性评分层：** 对每个候选人/JD 对象用同一套 `evaluate_pair` 产生资格、技能覆盖、核心职责证据、项目/经历证据、软条件和缺失信息；分别记录召回分与匹配分。方向和已通过的年限不能重复给固定加分。JD 找人、人找 JD 复用该评估器，保证同一对对象结论一致。
4. **可选 AI 深度复核：** 前端开关/按钮默认关闭，基本匹配结果先返回。用户启动后，后端异步对已召回的候选人逐批检查技术栈、工作/项目经历与 JD 核心职责，返回“推荐 / 待核 / 不推荐”、逐条证据 ID 与缺口。AI 只复核已符合可信硬条件的候选人，不得推翻明确硬条件。证据 ID 必须能回指当前 revision 的字段；无效引用、超时或模型不可用标记“未完成”，保留基本结果。最多展示约 30 人作为默认页面大小，不写死为总结果上限。

AI 复核使用现有生成式 AI provider 管理器与结构化输出校验；缓存键含 JD revision、简历 revision、分类/提示词版本与模型身份，编辑后失效。批处理有单次预算、并发限制、取消与进度；基本匹配接口不等待复核。展示基本匹配分和 AI 结论两个不同字段，不将 LLM 结论伪装成精确概率。真实简历和密钥不写测试夹具、日志或 Trae 对话；评测用脱敏或合成样本。

## 验证与发布合同

- 冻结独立数据库/索引快照；建立业务人员确认的搜索 query→相关候选人和 JD→候选人配对标签。旧版与每个变体在同一快照、同一模型、同一查询上比较，训练/调参集与最终验收集分开。不可用 `local-hash-v1` 证明语义相关性提升。
- 搜索报告 `Recall@50/100`、`Precision@10`、`nDCG@10`、字段筛选误伤数、无结果正确率、p50/p95 延迟及每次 embedding/rerank 数量；匹配报告资格违规数、池内召回、`Precision@5/10`、核心职责证据正确率、AI 开关前后增益、单次复核时延与成本。
- 必过用例：北京大学不触发北京现居硬筛；正文开关前后范围正确；AND/OR 技能组正确；无 MUST 证据不能被分数补偿；方向待核不静默丢失；双入口同对一致；AI 关闭无远程复核调用，开启后失败不改变基本结果。
- 切换向量版本必须先在 shadow 索引完成重建、兼容性检查、样本检索与回滚演练，再关闭应用切换；编辑、删除和新导入继续走已有 outbox/index sync，旧/新索引不能混写。
- 发布门槛：硬条件违规 0，必过用例全通过；独立验收集上主要搜索和匹配指标不能退化，至少一个预先指定的质量指标有改善；性能在约定交互预算内。若消融无收益，保留原向量文档，仅交付确定性修正与可选 AI。

## Trae 与 DeepSeek 的执行边界

Trae Agent 使用 DeepSeek V4 Pro **编写和验证项目代码**，与本应用在运行时选择哪个生成模型是两回事。Trae 官方把 IDE/SOLO 作为编码工作流，并说明项目规则与自定义 Agent 提示词的优先级；因此执行计划提供短的任务入口、准确路径和阶段验收，不依赖整份历史会话。DeepSeek 官方文档列出 JSON 输出和工具调用能力，但 2026-09 官方不同页面对 `deepseek-v4-pro` 的后续路由说明不一致；开工时须在 Trae 与应用 provider 中分别确认可用模型、响应格式、预算和实际路由，不能根据型号推断最终模型行为。
