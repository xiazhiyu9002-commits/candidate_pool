# 双向严格人岗匹配设计

日期：2026-09-15

## 目标与范围

只改「人才库 → 候选人列 → 匹配岗位」和「JD 管理 → 岗位列 → 匹配候选人」两个按钮。两边使用同一套准入判断；宁可漏掉合适结果或返回空，也不展示证据不足的对象。人才库搜索框的关键词、向量、混合检索仍保留。两个匹配按钮取消模式选择，统一走以下流程。

## 流程与准入合同

1. 读取当前、READY 的简历和 JD 版本；仅允许 AVAILABLE 候选人和 OPEN 岗位。先验证结构化字段和索引版本一致。缺失、无法归类、证据矛盾或服务失败均不视为通过。
2. 行业与职业方向为硬条件。职业方向使用系统**已有的统一口径**，本轮不重新建立职业方向分类；空值、`OTHER` 和现有口径判定不相容者不通过。行业另建有版本的「大类 → 细分行业」标准代码表，原始自由文本不直接作硬过滤值。JD 指向大类时允许候选人有该大类下的真实业务经历；JD 指向细分行业时要求对应细分业务经历。候选人可有多个经过原始工作/项目证据证实的行业代码；仅公司所属行业、宽泛的「IT/软件/AI」词不构成行业证据。无法可靠映射或来源不清时失败关闭。两个方向调用同一个行业归一化与准入函数。
3. 现有明确硬条件继续生效：年限、学历、岗位地点可接受性、排除项、状态等。JD 未写的条件不能凭空推导为硬条件；写了而简历证据缺失则不通过。行业和方向缺失的 JD 或简历显示「资料需补全」，不生成合格推荐。
4. 在 JD 导入/解析时，从现有 `required_skills`、`MUST`、`core_duties` 和原文证据中离线提出**目标 3～5 个、最多 5 个**具有辨识度的核心技能组，按「明确必须、岗位辨识度、职责证据」排序，再去重、识别真实等价别名和 AND/OR；通用软技能和加分项不占名额。这里复用已有解析，不在匹配按钮请求中增加 LLM 提词。候选人从工作/项目技术栈和技能字段离线提出目标 3～5 个专业关键词，仅用于岗位召回。JD 的建议组由业务人员核对后保存到当前 JD 版本；未核对或无可信核心组时显示「资料需补全」，不启动匹配。若原 JD 只有 1～2 个真正必须的关键词，保留 1～2 个并依赖职责证据把关，不为凑数发明词。超过 5 个时，另列的明确硬性资质仍须核对，不能因为不在关键词窗口而忽略。
5. 候选人关键词只用于岗位召回；最终必须逐项满足 JD 当前版本上**已经核对的全部核心技能组**，证据来源为当前简历的技能、工作或项目原文。Java/JavaScript、C++/C# 等边界要精确，`A 或 B` 可任选其一，`A 和 B` 必须都满足。仅画像总结或模型推断不能作技能证据。
6. 职责与经历的向量只用于找相似片段。JD 的 `core_duties` 对候选人工作经历、项目经历的原文片段；候选人的核心经历对 JD 的职责片段。每项关键职责要有可展示的来源片段、语义相关度及审核过的通过阈值；仅整份文档相似、行业相同、技能相同、总工龄符合均不足以通过。阈值以人工标注开发集校准，独立验收集不得调参。
7. 准入判断在重排序前完成，重排序只调整已通过对象的顺序。准入失败对象不落为合格匹配、不展示为推荐、不用弱相关项补足数量。关键依赖超时或索引不可用时返回明确的服务不可用状态，不能伪报「暂无合适结果」。内部排序分不得写成匹配概率或录用概率。
8. 展示行业、方向、核心技能组、职责经历的通过证据；每项证据能链接到当前简历/JD 版本中的具体片段。旧版本、已删除或状态变更后旧记录不得继续作为有效推荐。

## 可选 LLM 人岗分析

在已经通过准入的单条匹配结果上提供「生成 AI 人岗分析」按钮。用户点击后创建持久后台任务，匹配列表立即可用；页面展示排队、分析中、完成、失败状态。LLM 只读取这对人岗的当前原始 JD、简历片段和规则证据，输出契合点、风险与待核实问题及其来源。LLM 不新增推荐、不改变准入结果和排序。失败、超时或未配置模型时保留规则结果；相同简历版本、JD 版本和模型配置可复用已完成分析，版本变化后失效。默认不自动调用，后续可单独决定是否实现。

## 验收口径

- 招聘人员依据**原始** JD 和简历分别标注两个方向的开发集、独立验收集。进入结果的「明确不合适」或违反任一硬条件的数量为 **0**；已知无合适对象的用例必须返回空。允许合适对象被漏掉，但漏掉量及原因必须单列报告。
- 每个返回项的行业、方向、3～5 个核心技能组、职责经历与其他硬条件均能找到准确来源；影响准入的捏造证据为 **0**。测试必须覆盖分类缺失、错误大类、泛词、技能别名与边界、AND/OR、跨行业与跨方向、旧版本和依赖故障。
- 同一实体不能因多个简历、多个 JD 分片重复出现；两个按钮对同一人岗的准入结论一致。
- 正常路径测完整 API P95，并把向量、重排请求、费用和故障率如实记录。先沿用现有 5 秒完整 API 目标；若严格证据核对使其无法达到，要报告实际值和瓶颈，不通过放宽准入条件换取速度。
- 现有「十种选人方式」合同中的人才库三种搜索与精确筛选仍执行；其中双向匹配的六个模式指标由本设计的**两个统一匹配入口**替代，验收脚本和文档须同步更新，不能拿旧模式分数宣称新流程通过。
