# 人才库系统使用缺陷检查清单

> 用途：让一位招聘人员按真实工作顺序操作当前桌面应用，确认每项可见功能能完成任务、结果可信、出错时可理解，并记录 bug。本文是**待执行的检查方案**，不是已通过的测试报告。依据为当前 `desktop/src`、`backend/src/kerui_recruit/api`、`使用说明.md` 和 `搜索使用说明.md`；执行时以安装包实际界面为准。

## 1. 范围与通过口径

- 检查范围：启动与配置、简历入库、人才搜索、候选人编辑、JD 管理、双向匹配、招聘流程、看板、Mapping、BD 助手、邮件、备份恢复和常用桌面交互。
- 每项同时看三件事：**能不能找到入口、操作能不能完成、结果在刷新或重启后是否仍正确**。有外部依赖的项目另看失败提示和重试路径。
- 不做企业级扩展验收：不要求权限体系、多租户、审计平台、大规模压测或模型分数达到某个统一阈值。搜索与 AI 结果以预先标注的少量样本核对关键事实、硬条件和来源，不能仅凭“有结果”判通过。
- 一条用例记 `通过 / 失败 / 阻塞 / 不适用`。`阻塞`须写明缺少的服务、账号或样本；不能当成通过。未执行的用例留空。
- 发现“说明写了但界面没有”时，先核对当前安装包版本与入口；确认后记录为文档差异或功能缺陷，不自行假定它存在。

## 2. 执行准备

1. 在**独立测试数据目录**运行待测安装包，记录版本、构建时间、操作系统、数据目录。先做一份备份。不要在真实人才库上测试删除、恢复、批量操作和邮件发送。
2. 准备下面的小样本，文件内容由测试者掌握，手机号、邮箱均用虚构值；为每份样本写一张“应当识别的事实卡”。

| 编号 | 测试数据 | 预期用途 |
| --- | --- | --- |
| R1 | 可复制文字的 PDF 简历：上海、Java、5 年、本科、支付经历 | 正常导入、搜索、匹配、编辑、下载 |
| R2 | DOCX 简历：北京、Python、3 年、硕士、算法经历 | 多文件导入、排除条件、反向匹配 |
| R3 | 扫描版 PDF：姓名和至少一项可人工辨认的技能 | OCR、失败重试、人工复核 |
| R4 | R1 的重复文件；另加一份损坏或不支持的文件 | 去重、跳过与报错 |
| J1 | 开放的“上海 Java 支付工程师”JD，写明本科、3 年以上 | JD 解析、硬条件、人岗匹配 |
| J2 | 开放的“北京算法工程师”JD，写明 Python、硕士 | 反向匹配、岗位筛选 |
| O1 | 两层部门、两名员工的简短组织描述 | Mapping 导入、编辑与导出 |
| M1 | 测试邮箱中的一封白名单简历邮件、一封非白名单邮件 | IMAP 入库和白名单 |

3. 可选外部资源：一组可用的生成式 AI Key、SiliconFlow Key、Tavily Key、专用 IMAP/SMTP 测试邮箱。分别记录“已配置 / 未配置 / 连通失败”。不具备资源时执行本地路径和失败提示用例，外部成功用例记阻塞。
4. 执行顺序：先跑第 3 节主流程，再逐项跑第 4 节。每次更改数据后至少检查一次**当前页、其他关联页、重启后**的状态。删除类用例放最后。
5. 截图和日志不要包含真实简历、手机号、邮箱授权码或 API Key；缺陷记录可用测试编号代替个人信息。

## 3. 一次完整的用户旅程（优先跑）

按顺序执行，任一步失败先记录，能继续的后续步骤仍继续。这里的“正确”都以第 2 节事实卡和刚刚实际录入的事件为依据。

| 步骤 | 用户操作 | 应看到的结果 |
| --- | --- | --- |
| E01 | 首次启动，查看设置中的启动检查与数据目录 | 应用能进入首页；目录明确；未配置的服务显示可理解的状态，不能卡在白屏 |
| E02 | 上传 R1、R2，等待任务结束 | 成功/失败数量与所选文件一致；候选人能在列表找到；R1/R2 关键字段可核对 |
| E03 | 搜索“上海 Java 支付”，再用学历和年限筛选 | 能找到 R1；生效条件可见；R2 不应因语义相近而穿透硬筛选 |
| E04 | 导入 J1，检查原文与解析表，必要时人工修正 | 岗位、公司及要求可查看；保存后刷新仍是修正值 |
| E05 | 从 J1 匹配候选人，并从 R1 反向匹配岗位 | 结果能解释依据；J1/R1 对应正确；打开的是正确简历和 JD；可看到无匹配状态 |
| E06 | 从匹配结果为 R1×J1 建流程，填写发生时间，记录推荐、面试、结果、Offer、入职 | 阶段与时间线按操作推进；非法顺序被阻止；重开详情后事件仍在 |
| E07 | 打开看板，按 J1 和日期筛选，再导出 | 指标与刚创建的流程事件相符；图表、导出文件可打开且筛选范围一致 |
| E08 | 退出并重启应用，重新打开 R1、J1 和流程 | 关键编辑和事件仍在；搜索、匹配与列表没有孤儿数据或重复记录 |

## 5. 每个功能的通用“找 bug”动作

对上表每个会保存数据的功能，至少再做一次以下检查：

1. **空值与错误输入**：空文本、超长文本、错误文件类型、非法日期/范围；应拒绝并说明原因，不应静默成功。
2. **重复与连点**：连续点两次提交、断网后重试；不能重复建人、建岗位、建流程或重复发送邮件。
3. **中途离开**：任务运行时切页、关抽屉、重启；任务结果要能再找到，不能永远显示“处理中”。
4. **跨页一致**：编辑/删除后，列表、搜索、匹配、流程和看板不能各显示一套旧数据。
5. **失败后保留**：解析、AI 生成、下载、导出、备份失败时，原有资料和人工修改不能丢。
6. **可理解性**：用户能知道操作是否完成、下一步做什么、失败项是哪一条；按钮置灰时应能推断原因。

## 6. 缺陷记录与结束条件

每个失败只记一张缺陷卡，格式如下：

```text
缺陷编号：BUG-001
关联用例：C06
环境：安装包版本 / 系统 / 数据目录（测试目录）/ 外部服务状态
复现步骤：1. ... 2. ... 3. ...
预期：...
实际：...
发生频率：每次 / 偶发（n 次中出现 m 次）
影响：阻断主流程 / 结果错误或数据丢失 / 可绕过 / 仅提示或排版
证据：截图或日志文件名（脱敏）
临时绕过办法：有 / 无；如有，写具体步骤
```

优先修：①数据丢失或错关联；②导入→搜索→匹配→建流程任一主路径无法完成；③硬条件失效、误荐且界面无提示；④重复操作造成脏数据；⑤普通用户无法理解的失败。纯视觉瑕疵和高级设置的小问题排在后面。

本轮检查结束时，填写：`通过 __ / 失败 __ / 阻塞 __ / 不适用 __ / 未执行 __`，附缺陷编号清单。至少 E01～E08 走通且无未处理的主流程阻断或数据错误，才可写“核心使用流程可用”；外部依赖未跑完时明确写“有条件可用”，不要写“全部功能正常”。
