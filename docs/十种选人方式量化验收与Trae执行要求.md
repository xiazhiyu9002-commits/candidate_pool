# 十种选人方式量化验收与 Trae 执行要求

日期：2026-09-10。适用范围：当前 candidate_pool 系统。

这是本轮建议采用的产品验收门槛，不是行业统一标准，也不是当前系统已经达到的成绩。先测基线，再只修未达标项；全部达标后立即结束本轮优化。不训练或微调本地模型。

## 1. 本轮要交付什么

让“前几条值得看、明确要求不出错、已知合适结果不容易漏掉、响应时间能接受”成为可复测的结果。

不能以“系统自己打了 80 分”“接口返回成功”“结果比以前更多”“测试全部绿了”单独作为质量通过依据。推荐是否合适，必须依据原始简历、原始 JD 和独立评审标签判断。

本轮不追求招聘录用率、入职率等离线评测无法证明的结果。“可用”只代表值得招聘人员进一步查看和核实，不代表自动通过招聘决策。

## 2. 当前实现对验收的影响

已阅读当前源代码，以下是制定要求的依据；尚未运行十种方式的真实质量评测。

| 当前代码事实 | 验收时的处理 |
|---|---|
| 关键词检索已有词法规范化、别名与布尔查询路径 | 优先补失败用例，不从零重写检索系统 |
| 向量和混合模式都经过语义重排，关键词模式不经过语义重排 | 向量模式按“向量召回＋当前重排”整体验收，不能冒充纯向量实验 |
| 有重排分时，匹配评分使用相关性、技能覆盖、年限；无重排分时，主要依赖技能覆盖与年限，缺少对应要求时还会重新分配权重 | 不把不同模式的内部综合分直接当准确率；检查业务评分有没有覆盖原本合理的召回排序 |
| 候选人的关键词文本和向量文本不同，岗位匹配与反向匹配共用部分能力 | 修改公共逻辑后要回归两个方向，不能只验证人才库搜索 |
| 现有 search_golden.json 只有 6 条查询 | 保留为词边界回归，不能据此宣称十种方式整体达标 |
| search_acceptance.py 使用本地哈希向量与关键词重排器，定位是性能验收 | 不能用这套替身结果证明真实语义质量 |
| 搜索服务默认总预算为 4.5 秒，API 还有数据库读取、计分和记录等工作 | 分别记录搜索服务耗时和完整接口耗时，不把局部耗时当用户等待时间 |

主要定位：`backend/src/kerui_recruit/search/{service,documents,lexicon}.py`、`backend/src/kerui_recruit/match/service.py`、`backend/src/kerui_recruit/api/match.py`、`backend/src/kerui_recruit/bench/search_acceptance.py`。

已有“人才匹配十种方式详解”中的数据量和部分算法描述属于文档快照。本轮以 Trae 执行时的代码、有效数据和实际调用链为准，不直接沿用其数量或历史分数。

## 3. 先固定评审口径

### 3.1 相关性由证据决定

对每个“查询—人选”或“人选—岗位”组合，建立以下独立标签：

| 标签 | 含义 | 判定原则 |
|---|---|---|
| 3 | 高度合适 | 核心方向、主要能力有直接证据；没有明确硬条件冲突 |
| 2 | 值得进一步查看 | 核心方向合适、主要能力有证据，存在可接受的次要缺口 |
| 1 | 弱相关或待核实 | 仅有泛技能重叠，或关键能力缺少足够证据，不足以直接推荐 |
| 0 | 不合适 | 方向错误、明确硬条件冲突，或关键事实明显不符 |

标签 2、3 算“有效结果”。仅写过 Python 不足以认定会 Agent 架构；总工作年限不能直接证明某项专项经验年限。“简历未提及”应标为未证实，不能直接写成“不会”。

普通关键词检索按查询本意判定：搜索公司时，确有该公司经历就是相关；搜索技能时，核对技能证据。不要把招聘匹配标准错误套到姓名、公司等定位查询。

岗位匹配两个方向采用同一套事实证据和硬条件判断；允许因推荐目标不同而排序不同，不要求两边排名镜像一致。

明确的结构化硬要求优先。JD 的硬要求与用户附加条件按交集执行，不能用较宽松的 JD 条件覆盖更严格的用户条件。自然语言中未声明为硬门槛的“优先”“熟悉某框架”等，不擅自升级为一票否决。

冻结地点语义：现居城市筛选只看现居字段；意向城市筛选只看意向字段；岗位工作地的可接受匹配可用现居或明确意向城市，两个匹配方向保持一致。远程、多地点按 JD 的明确表达处理。需要调整已有界面语义时明确记录，不能为提高得分偷偷放宽条件。

### 3.2 三个质量指标

**前列有效率**：看用户最先看到的 K 条中，有多少条是标签 2 或 3。检索取 K=10，岗位匹配两个方向取 K=5。

为适应小型岗位库，使用以下明确的自适应口径，报告名称写作 `P_adapt@K`，不要冒充标准固定分母的 Precision@K：

```text
R = 冻结评审范围内所有已标注有效结果的数量
n = min(K, R)
P_adapt@K = 实际排名前 n 个位置中有效结果数 / n
```

少返回的位置按 0 分计。例如已知有 8 个合适岗位，要求看前 5 条，却只返回 1 个合适岗位，只得 20%；如果库里确实只有 2 个合适岗位，前 2 条都找到就得 100%。

当 R<K 时，再要求这类样例的平均 `Recall@K ≥90%`，且它们实际返回前 K 条中的无效结果比例平均 ≤20%：允许少返回，不允许用无关结果凑数。没有返回任何结果而 R>0，记为召回失败。R=0 的查询不进入正例均值，进入单独的无结果测试。

**关键结果找回率**：每个正例查询在调参前独立确定 1～5 个“肯定应该找得到”的结果 ID，计算它们进入前 20 条的比例，再对查询取平均。该指标是已知关键结果覆盖，不是全库 Recall@20。已选关键结果不得因某模式找不到而被删除。

**排序质量 nDCG@10**：根据 0～3 级标签，检查更合适的结果是否排在前面。使用增益 `2^标签-1` 和位置折扣 `log2(排名+1)`，缺失位置增益为 0；理想排序来自冻结的同一评审范围。理想增益为 0 的查询单列，不记成满分。

以上指标先逐查询计算，再对每种方式分别取平均。不能把结果多的查询加权到掩盖困难查询，也不能把十种方式混成一个总分。

此外，每种方式至少 80% 的正例查询，其前列有效率应达到 60%，避免平均分掩盖一批完全不可用的场景。

### 3.3 评审集规模与独立性

优先使用当前真实、有效、去标识化的数据副本，不为本轮专门造十万份简历。

| 评测内容 | 最小样例量 | 复用方式 |
|---|---:|---|
| 人才库检索 | 60 个正例查询 | 关键词、向量、混合共用；精确词/别名、语义表达、多条件组合各 20 个 |
| 人选匹配岗位 | 30 位不同候选人 | 三种模式共用；覆盖当前主要岗位方向与不同资历 |
| 岗位匹配人选 | 20 个不同岗位 | 三种模式共用；覆盖不同主要职责和约束 |
| 精确筛选 | 100 个条件用例 | 单字段 40、组合 40、缺失值/边界/矛盾条件 20 |
| 无合适结果 | 检索及两个匹配方向各 5 个 | 三种模式均运行；可在隔离数据副本中构造 |

同一人才库查询集同时跑三种检索模式，以支持公平比较。纯姓名/公司定位、语义改述等专属能力另外列分组成绩，向量模式不承担姓名精确查找必须成功的职责。

按查询意图或主体分组，约 2/3 用于开发、1/3 留作最终验收，固定随机种子。相同查询的同义改写、重复 JD、同一候选人的多个版本不能拆到两边。每一必要分组在最终验收集中至少 5 例；不满足就补样例，不能静默省略。

有合适岗位的候选人与无合适岗位的候选人分开统计。如果真实有效主体不足，使用全部真实主体并报告数量；合成边界例只能补确定性检查，不能宣称满足了真实主体的最小质量样本要求。

构建标签时：

1. 小库尽量评审全体可用岗位；候选人库较大时，使用三种模式各前 20 条的并集，加上独立查找到的正例与困难反例。
2. 标签必须引用原始内容证据，不能复制匹配分或系统解释作为答案。
3. 可由 AI 初评以减轻工作量，但招聘人员须抽审至少 20% 的组合，并审核所有争议项、硬条件争议、冻结前各模式前 5 条。未完成人工复核只能写“自动预评通过”，不能写“最终业务验收通过”。
4. 标签、数据副本、分组和关键结果 ID 在调参前冻结。不得根据改进后排名改答案。
5. 新版本返回未评审对象时先补做盲评；不能直接视为不相关，也不能默认为相关。标签集因此升级时，原始版本和最终版本都按新标签重算。
6. 使用候选结果池时，报告明确写“已标注结果池上的质量”，不能宣称测出了全库真实召回率。

最终验收集不能用于反复试参数。若验收失败，修复后保留原失败样例，并补充同类未见样例；不反复挑选最有利的一次运行。

## 4. 十种方式分别达到什么结果

所有数值都是最低通过门槛。每行的质量指标与专属要求必须同时达到，并通过第 5 节共用门禁。

| # | 方式 | 前列有效率 | 关键结果找回率（前20） | 排序质量 | 专属要求 |
|---|---|---:|---:|---:|---|
| 1 | 关键词检索 | P_adapt@10 ≥85% | ≥90% | nDCG@10 ≥0.80 | 指定词边界、别名、AND/OR 用例 100% 正确；在线 AI 调用为 0 |
| 2 | 向量检索 | P_adapt@10 ≥80% | ≥85% | nDCG@10 ≥0.80 | 语义改述组前列有效率 ≥80%；纯向量召回不得暗中调用关键词兜底并当正常成功 |
| 3 | 混合检索 | P_adapt@10 ≥85% | ≥90% | nDCG@10 ≥0.85 | 同一查询集上，前列有效率与 nDCG 各自不低于两种单模式较好值超过 0.02 |
| 4 | 精确筛选 | 返回集合正确率 100% | 应返回对象找全率 100% | 不评价相关性排名 | 100 个用例全部通过；分页取完后的 ID 集合必须与独立字段判定一致；AI 调用为 0 |
| 5 | 人选匹配岗位·关键词 | P_adapt@5 ≥80% | ≥85% | nDCG@10 ≥0.75 | 不能只因泛技能或年限相符就把明显不同方向岗位排入有效推荐；AI 调用为 0 |
| 6 | 人选匹配岗位·向量 | P_adapt@5 ≥80% | ≥85% | nDCG@10 ≥0.80 | 同义岗位名称与可迁移能力组前列有效率 ≥80%；关键能力必须有来源证据 |
| 7 | 人选匹配岗位·混合 | P_adapt@5 ≥85% | ≥90% | nDCG@10 ≥0.85 | 同一候选人集合上，前列有效率与 nDCG 各自不低于两种单模式较好值超过 0.02 |
| 8 | 岗位匹配人选·关键词 | P_adapt@5 ≥80% | ≥85% | nDCG@10 ≥0.75 | 技能词边界与等价别名通过率 100%；通用技能堆砌不能掩盖核心职责不符；AI 调用为 0 |
| 9 | 岗位匹配人选·向量 | P_adapt@5 ≥80% | ≥85% | nDCG@10 ≥0.80 | “做过相应工作但没有照抄 JD 词汇”组前列有效率 ≥80%；不能只按行业相似判断合适 |
| 10 | 岗位匹配人选·混合 | P_adapt@5 ≥85% | ≥90% | nDCG@10 ≥0.85 | 同一岗位集合上，前列有效率与 nDCG 各自不低于两种单模式较好值超过 0.02 |

混合模式不要求每个查询都赢，也不要求为胜过单模式不断增加 AI 调用；允许个别查询有差异，但整体不得明显退步。

指定词法例至少包含：Java 不误认仅有 JavaScript；JS/JavaScript、k8s/Kubernetes 等价；C++、C#、.NET、Node.js 边界保持；学校别名使用现有权威映射。严格 AND/OR 的集合语义必须正确，不能把 smart 模式误当严格 AND。

## 5. 十种方式共用的通过条件

### 5.1 正确性和解释

- **硬条件违规数为 0**：适用于所有实际返回结果，而非仅前 5/10 条。未知值不得被默认为“已满足”明确硬要求；有条件不足可供查看的结果必须单列为待核实，不混入合格集合。
- **失效结果数为 0**：已删除、不可用人选、关闭岗位和过期版本不得作为有效推荐。状态变更后应立即阻止旧结果继续有效展示；索引同步完成后更新内容可被检索。索引未就绪应准确提示。
- **重复实体数为 0**：同一个人或岗位不能因文本分块、多文档或旧版本占据多个名次。
- **分页/数量契约 100% 正确**：尊重实际 API 的 limit、分页和稳定排序约定；不得在评测脚本截断超额结果来掩盖接口问题。
- **解释证据准确率 ≥95%**：抽查至少 100 个结果，不足 100 则全部检查。按可核实事实条目计数，核对命中技能、缺口、年限和对应来源；捏造关键技能、学历、地点等影响判定的事实为 0 条。
- 规则要求的硬技能、加分项和“未证实”区分展示。不得把内部综合分称作录用概率。
- 每个方向的 5 个已知无合适结果用例，**100% 不给出明确合适推荐**。人才库可展示弱相关项，但必须提示缺少充分匹配，不能将其包装为合格结果。阈值根据开发集标定，不凭空统一用“80分”截断。

### 5.2 耗时与可用性

测量环境：同一电脑、同一数据副本、相同索引版本和实际配置的外部模型；完成索引预热后测量，但主验收不用应用结果缓存。缓存命中另列报告。

每种方式至少记录 50 次完整 API 请求，覆盖至少 10 个不同输入；正向匹配须计入落库和响应组装。P95 定义为排序后第 `ceil(0.95×N)` 个耗时。每种方式另做 10 次进程重启后的首请求并报告，首请求不混入常态指标。并发 1 作为主验收，并发 3 作可用性回归。

| 方式组 | 完整 API P95 上限 |
|---|---:|
| 关键词检索、精确筛选 | 500 ms |
| 两个方向的关键词匹配 | 1 秒 |
| 向量/混合检索、两个方向的向量/混合匹配 | 5 秒 |

搜索服务保留现有 4.5 秒预算；包含数据库与响应工作的完整 API 请求应在 5 秒内完成或给出明确超时/依赖失败响应，不能无限等待。主机调度带来的超限必须如实记录，不能删掉慢样本再算达标。

正常依赖环境中，正常完成率 ≥98%，异常或降级必须计入分母。正常质量指标必须使用真实 provider 的正常路径；另报全请求的可用性与降级比例，不能通过频繁降级获得性能达标。

注入 embedding 超时、rerank 超时、LLM 改写失败及索引未就绪，每类至少 5 例，处理正确率 100%：

- 关键词和精确筛选不受外部 AI 故障影响。
- 混合模式可保留通过硬条件验证的关键词结果，并明确标识降级。
- 向量 embedding 不可用时明确报不可用；rerank 不可用可以保留向量顺序并标识降级。
- 可选查询改写失败时使用原查询；不能改变已确认的硬条件。
- 错误不能伪装成“没有合适人选/岗位”，错误响应不能计作正常质量通过。

本轮以实际现有规模为主。已有大规模性能脚本可用于发现明显回退，但不要求新增十万级数据工程，也不能将合成数据速度当真实语义准确率。

### 5.3 AI 调用和优化成本

针对一次在线查询或一次单主体匹配，包含实际 HTTP 尝试次数：

- 关键词和精确筛选：embedding、rerank、LLM 请求均为 0。
- 向量和混合：正常路径 query embedding 至多 1 次，批量 rerank 至多 1 次；缓存命中可为 0 次。
- 可选 LLM 查询改写至多 1 次，默认关闭。仅人才库已有改写入口适用，不要求给两个匹配方向新增改写功能。
- rerank 每次最多 100 个候选文档，保持现有级别。不能逐候选人进行生成式模型问答，不能请求内重新 embedding 全库。
- 上述限制包含客户端隐式重试；失败采用已有预算内降级，不用反复调用突破次数和超时限制。
- 离线索引更新单独统计，不混入在线调用计数。只更新实际改变的内容；修改向量文本或模型时正确重建，禁止混用不兼容向量。
- 记录每种方式的请求次数、输入量、耗时及可获得的 token/费用。关闭可选改写时，按同一输入集和同一计价口径的平均在线成本不得超过基线 120%；若基线成本为 0，则报告绝对调用量与原因，不能计算无意义百分比。
- 无可靠单价时用调用次数和输入 token/字符量作代理，不能编造人民币成本。

只有基线未达标才考虑额外增强。可选改写若要被推荐为开启状态，需在独立验收集上使 nDCG@10 至少增加 0.02，同时不破坏其他门槛和成本约束；否则保持关闭。默认关闭状态也必须通过表中门槛。

## 6. 优化范围与顺序

这是允许的排查方向，不是全部必须开发的清单。

1. **事实和索引一致性**：当前版本、结构化解析、技能漏提、查询文本和索引文本是否用同一规则。先修数据流错误。
2. **关键词与技能逻辑**：词边界、真实等价别名、核心词权重、冗长技能短语拆分、AND/OR 的正确含义；不能把相关词无条件当等价词。
3. **硬条件与召回范围**：过滤前后是否丢失合格结果，召回池是否过小或被重复文档占满，两个匹配方向的条件是否一致。
4. **融合与最终排序**：RRF、重排输入、业务分权重和分数尺度；检查关键词匹配无重排时是否把词法相关性丢掉，检查年限分是否掩盖核心能力缺失。
5. **已有 AI 的输入与调用**：减少无关文本、保留关键证据，调整已有画像/解析/改写提示，批量重排、缓存和超时。默认复用现有模型，不以换更贵模型作为第一方案。

不训练或微调本地模型，不搭建新推荐平台，不迁移数据库架构，不全量重写检索模块，不追求每个历史样例完美排序。不能硬编码测试人选 ID、岗位 ID 或具体查询答案。

一次只验证一个有依据的改动。若改动未带来可测收益且并非必要正确性修复，则撤回。单一方向连续 3 次实验都没有收益时，停止重复试参数，重新分析失败原因；这不构成整体验收通过。

## 7. 达到什么条件才停止

Trae 应持续处理本轮范围内的未达标项，不能只写优化建议就宣布完成。

**正常完成必须同时满足：**

1. 十种方式在开发集和独立验收集上分别通过各自门槛；规定分组、稀疏正例、无结果例均通过，不能只看混合平均分。
2. 共用正确性、解释、性能、故障处理和 AI 调用门禁全部通过。
3. 既有严格契约不退步。已经达标的方式，主要质量指标下降不得超过 0.02 且仍达门槛；已有检索规范要求“不低于基线”的项目继续遵守其更严格要求。
4. 同一最终版本在独立验收集连续完整运行 2 次均通过；不换数据、不改标签、不改配置、不选最好的一次。关键词与精确筛选在固定数据上返回集合和顺序稳定；语义模式允许小幅排序差异，但两次都必须达标。
5. 完成与修改范围相关的后端回归、前端单元测试/生产构建及实际界面检查。至少检查人才库三模式＋精确筛选、人选匹配三模式、岗位匹配三模式的入口和实际输出。若改动分词/索引或打包依赖，补打包及离线关键词检索检查。
6. 提交第 8 节的证据，结论明确写出“10/10 达标”，才可将本轮标记完成。

**一旦全部满足，立即停止优化。** 不为了追求 90%/95% 继续改，不增加训练、模型或复杂架构。基线已经满足的功能可以完全不改。

若真实数据不足、评审标签尚未复核、外部服务不可用，或现有模型能力在限定范围内仍无法达标：不能降低阈值、伪造结果、无限重试或宣布完成。应报告“未验收通过/阻塞”，列出差距、失败证据、已尝试措施和所需条件；需要人提供材料时暂停依赖该材料的工作。这是如实报告边界，不是成功停止。

## 8. Trae 必须留下的结果

在 `docs/verification/selection-acceptance/` 保存以下文件，具体脚本位置可遵循现有工程结构：

- `baseline.json`：十种方式的初始成绩，包含缺失指标和失败原因。
- `dataset-manifest.json`：有效人选/岗位数、数据副本与标签版本、文件哈希、主体划分和随机种子、评审池范围、模型与索引版本。
- `labels.jsonl`：查询/主体 ID、被评对象 ID、0～3 标签、关键正例标记、来源证据位置、复核状态。保留在本地，不写入不必要的联系方式等个人信息。
- `final-run-1.json`、`final-run-2.json`：逐查询 ID、前 20 条实体 ID、标签、指标、完整 API 耗时、调用次数、降级/错误信息和各项门禁。
- `report.md`：十行“基线→最终→门槛→通过/失败”表；列明样本量、分组成绩、真实 provider 情况、成本变化、改动原因、残留失败例和结论。
- 可重复执行的评审脚本与精确命令。验收未通过返回非零退出码；缺少数据或 provider 只能 SKIP/BLOCKED，不能 PASS。

报告不得将自动预评等同于已完成人工业务验收，不得用硬编码结果代替实际 API 调用，也不得只提交一张“测试通过”截图。

## 9. 可直接复制给 Trae 的任务说明

> 请以 `docs/十种选人方式量化验收与Trae执行要求.md` 为本轮验收合同，基于当前系统完成十种检索/筛选/双向匹配方式的评测和必要优化。
>
> 先核实有效数据、当前配置与实现，固定评审口径和开发/验收集，跑真实 API 基线。按文档逐项处理未达标问题；已达标项保持，不为优化而优化。优先修事实与索引一致性、词法/技能识别、硬条件、召回和排序，再考虑已有 AI 输入与调用方式。不要训练本地模型，不新增复杂架构，不逐人调用大模型，不用 mock 语义结果宣称业务达标。

## 10. 评测方法参考

固定数据、查询和相关性标签是信息检索评测的基本组成；较大集合可采用多种检索方法结果并集建立评审池。参见 Stanford《Introduction to Information Retrieval》的 [系统评测](https://nlp.stanford.edu/IR-book/html/htmledition/information-retrieval-system-evaluation-1.html)、[相关性评审](https://nlp.stanford.edu/IR-book/html/htmledition/assessing-relevance-1.html) 和 [排序结果评测](https://nlp.stanford.edu/IR-book/html/htmledition/evaluation-of-ranked-retrieval-results-1.html)。本文的数值门槛、自适应前列有效率和停止条件是针对本项目提出的产品要求，不来自上述文献。
