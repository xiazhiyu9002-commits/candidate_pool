# 检索与双向匹配语义盲评、职业方向策略评估（2026-09-17）

## 结论摘要

- 纯向量检索是当前最明显的短板：24 个检索意图中 6 个无结果；按脱敏证据由独立模型评定的平均 P@5 为 0.375，混合为 0.858。该 P@5 是小样本模型评测，不等于真实猎头满意率。
- 当前匹配存在明确的漏检和误荐。10 个岗位找人请求共返回 14 人，独立模型对这 14 对判定为 8 对直接推荐、4 对待核、2 对不推荐；5 个人找岗位请求共返回 5 个岗位，其中 3 个人的结果为空。样例为定向抽样，不可外推为全库准确率。
- 职业方向等值过滤发生在召回前。一个前端 JD 三种模式均返回 0，但冻结数据中至少有 3 位方向为空、前 5 项技能全部命中、近期主职责明确为前端开发的候选人。最终评分里给方向 10% 权重无法救回他们。
- 单纯取消方向硬筛也不够：数据分析 JD 已返回两位同属 DATA 的候选人，但其工作主线分别为大数据平台和数据治理产品，独立模型均判不推荐。必须把核心职责、项目交付和技能组语义一起纳入筛选。
- 推荐采用“扩展召回 + 有证据的方向评分/条件排除 + 职责重排”，而不是固定单选方向硬筛，也不是无条件纯加权。下文的比例与阈值是待 A/B 校准的初值。

## 评测范围与判分

使用 `.semantic-audit-snapshot` 中 2026-09-17 冻结的数据库和索引副本，以当前 `HybridSearchService` / `MatchService` 实际运行路径取结果。数据包含 1713 条当前 READY 简历修订、80 个 OPEN JD；一个人可能有多份当前修订，1713 不是人数。搜索覆盖 24 个非精确筛选意图，关键词、向量、混合各取前 100；匹配覆盖 10 个 JD 找人、5 个人找 JD，请求分别运行三种模式。本报告主要展示向量、混合及双向匹配的 hybrid 基线。

脱敏卡片只保留年限、技能、画像摘要、近期职责和项目证据；独立模型为 `deepseek-flash`，不知道检索模式和排序，按 0=不相关、1=仅术语接近、2=可面谈但有关键待核、3=职责和交付直接吻合评分。我另按猎头初筛规则看主要职责、项目交付、业务场景、资历和硬条件，不把模型分数当真值。P@5 按相关等级 ≥2 计算；Recall@50/100 的分母仅为三模式结果并集，属于池内召回代理指标，不能称为全库召回率。抽样与单模型均可能有偏差。

原始脱敏证据：`.semantic-audit-snapshot/retrieval.json`、`blind_cards.json`、`blind_labels.json`、`search_metrics.json`、`match_results.json`、`match_blind_cards.json`、`match_blind_labels.json`、`direction_blind_cards.json`、`direction_blind_labels.json`。所有编号均为不可逆短哈希。

## 五、职业方向：现状、量化标准与是否新增

冻结库里 1713 条当前 READY 简历修订中，方向空值 359、OTHER 140、非法值 1；80 个 OPEN JD 中空值 46、OTHER 2。52 份定向脱敏卡片中，库内标签与独立模型主方向一致 40 份，不一致 12 份；这是刻意选边界案例，**不是 23% 的总体分类错误率**。典型争议：iOS SDK 开发记为 BACKEND 而模型判 FRONTEND；数据/产品负责人因管理 60–135 人被模型判 MANAGEMENT；测试组长方向为空；SAP FICO 实施被记为 OPS。一个单选字段同时承担“专业”和“是否管理”的任务，本身就会制造冲突。

建议将**主专业方向**与**管理属性、细分专长**分开存储；保留一个最可能主方向供展示，同时输出第二方向、置信度、引用的职责/项目证据。历史方向为空不要求用户逐条手工确认，但不得在召回前自动丢掉。现有 `MANAGEMENT` 可先作为兼任标签兼容，迁移后不再与技术专业互斥。

以下为待标注集校准的判定初稿：候选人最近两段实际职责/交付占 50 分，代表项目的个人动作与产出占 30 分，最近职位名占 10 分，技能表占 10 分；JD 以核心职责 60、可验交付 25、标题 10、工具 5 计。每项必须给出处；只有技能/标题、没有职责或项目证据时，任何方向不得评“高置信”。最高方向 ≥70/100 且领先次方向 ≥20 分、证据来自至少两种独立来源，才算高置信；50–69 或领先不足 20 分保留第二方向；低于 50 分为低置信，但仍可给出展示用最可能方向。这些阈值**尚非实测最优**。

| 现有方向 | 决定性职责/交付证据 | 易混淆但不得单独决定的信号 |
| --- | --- | --- |
| BACKEND | API/业务服务、交易/分布式系统、数据平台与采集处理服务、Agent 应用编排和工具接入的生产交付 | 只用 Java/Python；做数仓指标或训练模型应看主交付 |
| FRONTEND | Web/移动客户端界面、交互、组件/跨端架构、iOS/Android 客户端或 SDK 交付 | 会 React 或写 BFF 不足以代表主业 |
| ALGORITHM | 模型训练/微调、推荐搜索算法、离线评测或推理算法优化的个人产出 | 仅接 LLM API、RAG 或 Agent 工作流属于应用工程 |
| DATA | 数仓主题/模型、指标体系、BI、数据治理与业务分析的可用交付 | 仅做数据接入、流处理服务或平台 API 时偏 BACKEND |
| OPS | 生产环境可靠性、发布、监控、故障响应、云基础设施运维 | 开发项目中使用 Docker/K8s 不够；SAP 财务实施另判 |
| QA | 软件测试策略、自动化测试框架、质量验证与缺陷闭环 | 开发者写单元测试不够；制造业质量管理不等于软件 QA |
| PRODUCT | 用户问题定义、需求取舍、路线图、PRD、验收与产品效果负责 | 只做项目排期/交付或研发管理不够 |
| MANAGEMENT | 团队编制、招聘培养、绩效/预算、跨团队交付结果为主要责任；同时记录原专业 | 技术负责人/项目负责人头衔或带一两个项目不够 |
| OTHER | 明确在当前招聘范围之外的职能；须说明具体职能 | 信息缺失、解析失败或多方向冲突不应直接记 OTHER |

**是否增加方向：**先不把“数据工程”“Agent 工程”“全栈”各拆成一个互斥大类，使用上述主专业 + 细分标签/第二方向。按近期职位名粗筛，36 位候选人的头两段职位涉及移动客户端，其中 11 位当前为 OTHER；18 位涉及安全，其中 7 位当前为 OTHER。当前 80 个 JD 的标题没有明确移动端或安全岗位，因此建议先补 `MOBILE/CLIENT`、`SECURITY`、`EMBEDDED` 专长标签并抽样复核；当对应岗位实际出现且同一大类内职责差异持续造成误检时，再评估独立主方向。iOS/Android 应先纳入 FRONTEND 的客户端定义；安全治理、应用安全、SRE 也应按主要交付细分，不可仅凭“安全”一词建类。

## 六、硬筛与加权：同一数据上的取舍

当前方向已经在最终总分里占 10%（有值时），但 `_hard_filter` / 反向检索先把它作为索引等值条件，`LanceDBSearchIndex` 执行 `direction = ...`。因此只调 10% 的权重不会改变候选池。另一方面，`evaluate_pair` 允许 null/OTHER 方向继续，召回前的等值过滤却挡住这批人，两个阶段策略不一致。

| 策略 | 这次样例中的收益/风险 | 判断 |
| --- | --- | --- |
| 现有单选方向硬筛 | 前端 JD 0 人，至少 3 位方向为空的强相关者无法进入候选池；DATA/BACKEND 交界也可能漏人 | 不宜继续作为唯一召回入口 |
| 完全取消硬筛、只给方向权重 | 能救回跨类和缺值者；但数据分析 JD 的两位同方向误荐仍在，宽泛技能/方向可能顶到前排 | 不能单独解决精准度 |
| 扩展召回 + 证据重排（建议） | 同向/次向与全方向救援并行，再依据近期职责、项目交付和明确 MUST 分组排序；高置信且职责确实冲突时再排除 | 最适合先做离线 A/B |

建议在 2000–5000 份规模先各取约 70 个同向/相邻方向、30 个全方向语义/关键词救援位，去重后维持 50–100 人候选池；不够时动态补足。候选池的初始排序可试职责 35%、明确必备技能 25%、项目/场景/规模 20%、资历 10%、方向 10%。地点、学历等**JD 明确的真实硬条件**另行检查；“或”技能组和可替代工具不能展开成多个独立 MUST。仅在两侧方向均高置信且职责证据互不相容时，才考虑条件排除。前端可选 AI 深度复核继续默认关闭，对较小候选池补充“推荐/待核/不推荐”及证据；它不替代召回。

这组比例不是上线标准。先在当前盲标集及补充人工标注集比较三策略的 Recall@50/100、强相关 Precision@10、显著误荐数、漏检数与延迟；尤其复测本文的前端、数仓、Agent、数据分析、交易系统案例。只有能同时救回明确漏检且不显著增加误荐，才调整生产策略。

## 优先处理的问题

1. 统一方向在召回和最终资格阶段的语义：null/OTHER、次方向和 BACKEND↔DATA、BACKEND↔ALGORITHM、FRONTEND↔BACKEND 等交界应有救援通道；新旧索引需按新字段重建。
2. 改 JD 技能抽取：区分真正硬必备、可替代的 OR 组、偏好和通用能力；“前端工程化”“关系型数据库”“CrewAI”等不能无证据地变成绝对门槛。
3. 对职责和项目的**个人动作、业务场景、规模**做重排与解释。仅按 DATA/BACKEND 大类相同会保留明显误荐。
4. 用同一盲标集对向量相似度阈值及父/子向量文本 A/B/C 做消融；目前有 6/24 个纯向量查询空结果，先找回阈值前原始分数再改阈值。
5. 建 30–50 个由实际招聘人员复核的边界配对作为稳定验收集。独立模型判断可用于发现问题，但不能作为最终真值。

本报告只做评测与方案设计，未改生产匹配代码或提示词。
