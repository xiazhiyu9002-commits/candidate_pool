# 十万候选人离线搜索验收

执行日期：2026-09-01。仅使用临时合成数据，没有读取真实简历、真实业务库或调用外部模型。

## 数据与环境

- SQLite 候选人计数：100,000。
- LanceDB 去重候选人计数：100,000；片段计数：300,000，每人 3 个片段。
- 64 维确定性本地 hash 向量；本地关键词重排。两者只验证调用链、耗时与降级，不代表语义模型准确率。
- Windows 本机，Intel Core i7-13700H，14 核 / 20 逻辑处理器。未隔离其他进程，也未清空操作系统文件缓存。
- 实际经过 HTTP ASGI 路由、LanceDB 全文与向量召回、过滤与排除、候选人去重、SQLite 当前实体及待同步状态核验、响应序列化。没有 TCP、桌面 UI、联系人解密或远程模型传输成本。
- 两轮测量均在建库进程退出后的新 Python 进程中进行。因此“首请求”表示进程/连接首次访问，不表示操作系统冷缓存。
- 建库用时 18.06 秒；数据位于系统临时目录，未写入真实数据目录。

## 硬截止与降级

受控 embedding / reranker 等待 20 秒，搜索不给它们额外截止时间。重复轮实测：

| 慢依赖 | 总预算 | 响应用时 | 结果 | 解释 |
|---|---:|---:|---:|---|
| embedding | 200 ms | 172.56 ms | 0 | 本地全文也未及时完成，明确 `service_error`，不伪报无匹配 |
| reranker | 200 ms | 183.24 ms | 0 | 召回或当前事实核验预算不足，明确降级 |
| embedding | 1,000 ms | 897.74 ms | 20 | 保留已完成的全文召回，`EMBEDDING_UNAVAILABLE` |
| reranker | 1,000 ms | 910.09 ms | 20 | 保留融合结果，`RERANKER_UNAVAILABLE` |

另外，小型受控回归验证：完整排除证据读超时不会放行候选人；取消调用不会声称已停止原生线程；线程数量受共享池限制；超时后候选人扫描不会继续启动新分页查询；不响应取消的异步 provider 任务数量也受限。

## 可重复执行

在 `backend` 目录下使用项目虚拟环境，创建一个全新的临时目录：

```powershell
$benchmarkRoot = Join-Path $env:TEMP ('kerui-search-acceptance-' + [guid]::NewGuid().ToString('N'))
& ../.venv/Scripts/python.exe -m kerui_recruit.bench.search_acceptance build --root $benchmarkRoot --candidates 100000
& ../.venv/Scripts/python.exe -m kerui_recruit.bench.search_acceptance measure --root $benchmarkRoot --queries 60 --concurrency 5 --output ../docs/verification/search-100k-rerun.json
```

实现：[search_acceptance.py](../../backend/src/kerui_recruit/bench/search_acceptance.py)。原始逐请求数据：[第一轮](2026-09-01-search-100k.json)、[重复轮](2026-09-01-search-100k-repeat.json)。

## 不能据此得出的结论

这不是生产模型、真实长简历、高维向量、网络波动或更高并发下的性能保证，也不是检索准确率验收。短文本重复模板与 64 维向量会低估真实部署成本。首请求差异也显示缓存和机器活动的影响。原有 `tests/performance/test_search_budget.py` 只验证 12,000 候选人，其旧 `BenchmarkApp` 报告的 `concurrency` 参数没有实际启动并发；本报告的并发数据来自新脚本的真实并发 HTTP 调用，不借用旧报告的名义并发数。
